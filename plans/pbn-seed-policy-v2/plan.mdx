title: PBN seed batches get a real content policy
objective: Give each PBN seed batch an explicit, auditable policy for badges, bio text, main image and expiry, so a seeded batch stops looking like 90 identical clones of the source market.
status: awaiting review
owner: Ian K
date: 2026-09-04
scope: PBN seed policy schema, provisioning meta writes, a bio-rewrite stage, main-image rotation, expiry stamping, and the Seed wizard Setup step
non_goals:
  - Changing the destination theme's homepage query (newest-100 pool, shuffle, card limit) — that is a manual theme upload on each PBN site, tracked separately

  - Rewriting media storage or the two-stage media pipeline itself

Today every profile a seed batch creates is the same shape: basic tier, no expiry,
the source's bio verbatim, and the source's lead photo. `storeProfileMeta` writes
`premium=0`, `featured=0`, `verified=0` unconditionally, so the `vip_flags` and
`verification` copy-policy options that already exist are dead — they cannot
change the outcome. Nothing writes `escort_expire` at all.

Two things follow. The obvious one is that the destination site reads as
generated. The less obvious one is a visibility problem: the destination
homepage's VIP and Premium sections query `featured=1` and `premium=1`, which are
separate pools from the capped basic pool. A batch where every profile is basic
can only ever compete in the one pool that is capped and shuffled.

This plan makes the four content decisions explicit, per batch, and records what
each profile actually received.

## Approach

The four levers attach at four points that already exist. None of them needs a new
pipeline — each is a decision inserted where the value is currently hard-coded.

## The policy shape

`copy_policy` is already a JSON column on both `pbn_sites` and `pbn_seed_batches`,
merged through `PbnSite::effectiveCopyPolicy()`. The new keys are additive, so
existing sites and historical batches keep working — `array_replace_recursive`
fills the defaults for anything absent. No migration is needed for the policy
itself.

## The badge write is currently unreachable

This is the specific defect that makes today's `vip_flags: copy` option inert. The
loop above it writes whatever the payload carried, and then three unconditional
lines overwrite all of it.

## Bio rewriting

`AiGateway::generate($feature, $system, $user, $opts)` already runs a provider
waterfall across Claude, OpenAI, Gemini and DeepSeek, and persists an
`ai_interactions` row per call with provider, latency and cost. Reusing it means
bio rewriting inherits the fallback chain, the cost accounting and the audit log
for free. The new service supplies the feature slug `pbn_bio_rewrite` and the
prompt; it owns no provider logic of its own.

The prompt must preserve the facts a reader acts on — the working name, the city,
services, rates and contact details — while changing sentence structure and
wording. It must not invent attributes. The rewritten text is stored on the item
before the WordPress insert, so a failure is visible in the CRM rather than
producing a half-written profile on the destination site.

<Callout tone="risk" title="Rate and latency" body="90 sequential provider calls at roughly 1–3 seconds each is 2–5 minutes of queue time on top of provisioning. The bio stage runs inside the existing per-item provisioning job, so it is already chunked and already retryable — but the batch will visibly take longer than today's. The wizard shows an estimated cost and a longer ETA before queueing." />

## Verification

Beyond `--filter='PbnSeedPolicy|PbnSiteTest'`, the batch has to be watched end to
end on a real site, because the failure modes here are all at the WordPress
boundary rather than in PHP.

1. Revert the existing Manuel batch through the current revert flow and confirm the item rows reach `reverted`.
2. Queue a deliberately small batch — 6 profiles across two Jinja destinations, 33% featured — and let it run to `created`.
3. In phpMyAdmin on Manuel, read the `postmeta` rows for those six post IDs and assert `featured`, `premium` and `escort_expire` match the `applied_policy` recorded in the CRM.
4. Open the destination homepage and confirm the featured profiles appear in the VIP section, which has been empty on that site until now.
5. Open two of the seeded profiles and confirm the bios differ from their source profiles in wording while keeping the same phone number, and that their lead photos are not the source's lead photo.
6. Only once that batch is verified, queue the full replacement batch.
