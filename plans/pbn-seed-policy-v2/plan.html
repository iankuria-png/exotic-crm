Implementation plan

PBN seed batches get a real content policy

Give each PBN seed batch an explicit, auditable policy for badges, bio text, main image and expiry, so a seeded batch stops looking like 90 identical clones of the source market.

Status awaiting reviewOwner Ian KDate 2026-09-04Scope PBN seed policy schema, provisioning meta writes, a bio-rewrite stage, main-image rotation, expiry stamping, and the Seed wizard Setup stepNon-goals Changing the destination theme's homepage query (newest-100 pool, shuffle, card limit) — that is a manual theme upload on each PBN site, tracked separately; Reverting the existing Manuel batch — the existing revert flow already covers it; Rewriting media storage or the two-stage media pipeline itself

Today every profile a seed batch creates is the same shape: basic tier, no expiry, the source's bio verbatim, and the source's lead photo. storeProfileMeta writes premium=0, featured=0, verified=0 unconditionally, so the vip_flags and verification copy-policy options that already exist are dead — they cannot change the outcome. Nothing writes escort_expire at all.

Two things follow. The obvious one is that the destination site reads as generated. The less obvious one is a visibility problem: the destination homepage's VIP and Premium sections query featured=1 and premium=1, which are separate pools from the capped basic pool. A batch where every profile is basic can only ever compete in the one pool that is capped and shuffled.

This plan makes the four content decisions explicit, per batch, and records what each profile actually received.

Approach

The four levers attach at four points that already exist. None of them needs a new pipeline — each is a decision inserted where the value is currently hard-coded.

Where each policy lever attaches
1 · Batch creation — PbnSeedPreviewService::createBatch
Resolves the batch policy into a per-item decision: badge tier, expiry timestamp, main-image index. Written to pbn_seed_items.applied_policy.
2 · Bio stage — PbnSeedBioService (new)
Runs inside provisionItem before the WordPress insert. On provider failure the item falls back per policy rather than failing the create.
3 · Meta write — WpDirectProvisioningService::storeProfileMeta
Stops hard-writing premium/featured/verified to 0. Writes the resolved badges and escort_expire instead.
4 · Media stage — PbnSeedMediaService::processItem
The is_main flag comes from the item's recorded image index instead of index === 0.

The policy is resolved once per item at batch creation and recorded, so provisioning and media both read a decision rather than making one.

Policy is resolved once, at batch creation

Badge tier, expiry and main-image index are decided when the batch is created and stored per item, not recomputed during provisioning. Provisioning and the media stage run in separate queued passes and the media stage retries independently — recomputing a random choice in either pass would give an item a different badge on retry than the one the preview promised. Recording the decision also makes a batch reproducible and reviewable after the fact.

Percentages are of the batch, not per profile

A 10% VIP setting on a 90-profile batch means exactly 9 profiles, allocated by shuffling the item list and taking the first 9 — not a 10% dice roll per profile that can land on 3 or 17. Small batches stay predictable, and the wizard can show the resulting counts before you queue.

The policy shape

copy_policy is already a JSON column on both pbn_sites and pbn_seed_batches, merged through PbnSite::effectiveCopyPolicy(). The new keys are additive, so existing sites and historical batches keep working — array_replace_recursive fills the defaults for anything absent. No migration is needed for the policy itself.

Bio rewriting

AiGateway::generate($feature, $system, $user, $opts) already runs a provider waterfall across Claude, OpenAI, Gemini and DeepSeek, and persists an ai_interactions row per call with provider, latency and cost. Reusing it means bio rewriting inherits the fallback chain, the cost accounting and the audit log for free. The new service supplies the feature slug pbn_bio_rewrite and the prompt; it owns no provider logic of its own.

The prompt must preserve the facts a reader acts on — the working name, the city, services, rates and contact details — while changing sentence structure and wording. It must not invent attributes. The rewritten text is stored on the item before the WordPress insert, so a failure is visible in the CRM rather than producing a half-written profile on the destination site.

Rate and latency

90 sequential provider calls at roughly 1–3 seconds each is 2–5 minutes of queue time on top of provisioning. The bio stage runs inside the existing per-item provisioning job, so it is already chunked and already retryable — but the batch will visibly take longer than today's. The wizard shows an estimated cost and a longer ETA before queueing.

Verification

Beyond --filter='PbnSeedPolicy|PbnSiteTest', the batch has to be watched end to end on a real site, because the failure modes here are all at the WordPress boundary rather than in PHP.

  1. Revert the existing Manuel batch through the current revert flow and confirm the item rows reach reverted.
  2. Queue a deliberately small batch — 6 profiles across two Jinja destinations, 33% featured — and let it run to created.
  3. In phpMyAdmin on Manuel, read the postmeta rows for those six post IDs and assert featured, premium and escort_expire match the applied_policy recorded in the CRM.
  4. Open the destination homepage and confirm the featured profiles appear in the VIP section, which has been empty on that site until now.
  5. Open two of the seeded profiles and confirm the bios differ from their source profiles in wording while keeping the same phone number, and that their lead photos are not the source's lead photo.
  6. Only once that batch is verified, queue the full replacement batch.
Open questions
  1. Q1Should the policy be allowed to set the verified badge at all?single

    On the live sites the verified badge asserts a KYC check that a seeded profile has not been through. Allowing it is a product decision rather than a technical one, and it is the one badge that makes a claim about a person.

    • Ship it, defaulted off recommendedThe control exists and is set to 0% by default, so enabling it is a deliberate act rather than an accident.
    • Do not build itOnly featured and premium are configurable; verified is always 0 for seeded profiles and the control never appears.
    • Ship it, defaulted on at a low percentageTreated like the other badges, with a small share of the batch marked verified.
  2. Q2Should the batch stagger post_date so profiles do not all land in the same minute?single

    Provisioning stamps post_date at insert time, so a 90-profile batch produces 90 posts within a few minutes. That is both a visible pattern and the reason an older batch drops out of the destination's newest-100 homepage pool all at once. Spreading the dates changes how the batch behaves on the destination site, so it is worth deciding now rather than retrofitting.

    • Backdate across a window recommendedSpread post_date across the last N days, oldest first, so the batch looks like organic signups accumulating rather than one import event.
    • Drip the queue over hoursKeep post_date as insert time but pace the provisioning jobs so creation genuinely spreads out. More faithful, but the batch takes hours to complete and is harder to supervise.
    • Leave as isAll profiles carry their true creation time.
  3. Q3Ship all four levers together, or land the cheap three first?single

    Badges, expiry and image rotation are self-contained and testable in a single pass. Bio rewriting adds a provider dependency, per-batch cost and several minutes of queue time, and it carries the fact-preservation risk. Splitting lets a replacement batch go out sooner.

    • Badges, expiry and image first recommendedLand steps 1–4 and 6–9 in one push, then add the bio stage as a follow-up once a batch has been verified end to end on Manuel.
    • All four togetherOne larger change; the replacement batch waits until the bio stage is verified too.
