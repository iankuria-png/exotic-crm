## Intake and reconciliation contracts

Verify the exact raw body using the pinned application's API key, consistent with the installed K2 SDK's SHA256 HMAC verifier; do not try multiple keys or accept a parsed/re-encoded-body signature. Reuse the selected production KopoKopo profile's credentials without changing its STK till. Restrict outbound hosts to the environment's official KopoKopo host and expected API paths; disable redirects and never trust payload links.

Accept K2Connect received/reversed events only for 268491, KES and confirmed statuses. Validate decimal money without floats, reference/resource identifiers, sender phone/hash shape and offset-bearing provider timestamps. Retain bounded encrypted bodies before acknowledging. Unknown formats/events and event-ID/content conflicts have durable review evidence; event retries and resource/reference identity conflicts cannot allocate twice. Reversal state is sticky, including reversal-before-credit. Delivery does not create or complete a CRM payment by itself.

Polling uses the documented asynchronous v2 API. Persist the exact requested window, callback request UUID and expected provider ID/location. Callback signature, feed, request ID, returned window, till, status and all transaction rows must pass before marking coverage complete. Provider callbacks can arrive before the POST response: retain/request-correlate them and reconcile safely. Poll failures and uncertain subscription/poll requests remain visible; do not blindly repeat an ambiguous external POST. Recovery includes GET of the stored polling resource, overlap windows, bounded limits and scheduler locking. Only completed contiguous coverage advances the cursor; quiet tills are not declared offline simply because no customer paid.

Provider identity uses `CollectionPrivacy::fingerprint('kopokopo:'+account_id+':hash:'+lowercase_provider_hash)` when a hash is supplied; phone-only evidence uses a separate `:phone:` namespace and normalized Kenya phone. Never calculate or guess a provider hash from the phone. Hash is canonical when available. Phone enrichment preserves the existing hash fingerprint; phone-only observations cannot downgrade it. A later verified hash on the same resource/reference may replace a provisional phone fingerprint, with an audit entry, cleared suggestions and version increment; old reviewed payer links are not silently transferred to the new fingerprint. Conflicting nonempty hashes/phones are review holds. CSV and webhook hash values share the exact namespace; live equality still needs acceptance.

Reversal-before-dispatch blocks fulfillment. Reversal-after-activation flags the receipt for staff and the established correction workflow; it does not automatically revoke service, issue a refund or suspend unrelated receipt intake. A later credit never clears a reversal.

CSV import previews the report and exact till, refuses malformed rows/different currency/till, deduplicates reference/status observations and records source digest/actor. Apply is explicit. Every CSV row is historical regardless of date; it cannot make an existing live receipt historical or change live epoch ownership. Import conflicts and reversals require review; trusted history is advisory and never retrospectively activates.
