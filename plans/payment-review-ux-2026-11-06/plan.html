Review incoming payments with payer identity and explained suggestions

Show the SMS payer, count prior payments using their number, and preselect a supported client so staff can approve or change the purchase in one drawer.

Status live — independently verifiedOwner Ian KuriaDate 2026-11-06Scope Tanzania receiving-payment workspace, read-only matching context, and reviewed purchase selectionNon-goals Changing payment activation gates, WordPress writers, pricing, or automatic renewal authority; Importing the historical SMS archive or changing the phone APK

The current Payments screen shows a masked payer and an empty purchase form. The parser already extracts the phone, but drops the name. Existing candidate selection requires a reviewed purchase intent; it cannot suggest a first-time profile from payment history or the advert phone.

The new review drawer opens with payer evidence, then a ready-to-review client choice. SMS payer identity and advertiser profile identity have separate labels because a customer may pay through someone else. All names, numbers, counts and scores in the wireframes below are synthetic examples, not production customer records.

Identity and history contract

Reuse encrypted CollectionEvent.normalized and CollectionReceipt.payer_phone. Add read-only payer-name extraction to TzMpesaParser and a new CollectionReviewContextService; no schema change is required. Parse the already captured receiving events linked to each receipt, validate sender/account/reference, deduplicate complementary bodies and retain source event IDs in the returned evidence. Four supported layouts include phone plus name, name only, bank summary, and bank-prefixed phone/name. Keep an explicit bank/source label separate from a person name; uncertain party text is labelled “SMS sender details”, never asserted as a full personal name. A missing or conflicting name remains explicit. Existing saved events can supply the display immediately without reprocessing ingestion, changing receipt versions or replaying the outbox.

Expose the full payer phone and supported name only through the authenticated, account-scoped collection endpoints already restricted to admin/sub_admin/sales. Keep both hidden in generic model serialization, logs, global badges and exports. The existing CSV export remains unchanged in this slice. The queue and drawer batch-load only parsed SMS events for visible receipts, capped at 200 per receipt; if capped or inconsistent, return incomplete evidence and suppress unsupported suggestions. Never query the phone's general inbox or export personal/OTP messages.

“Prior payments” counts distinct earlier positive subscription cash transactions using the exact normalized payer phone in the receiving account's currently bound and staff-visible markets. It excludes the current receipt and any CRM row representing it, future-dated payments, free trials/zero rows, test/sandbox records, failed/cancelled/reversed/invalid-reference transactions, and visitor/tour/wallet purchases. Reuse Payment::reportableSuccessful() including businessVisible() to preserve current test, bundle-visibility, resolution and manual-review exclusions. Collapse eligible committed ManualPaymentBundle children to one cash transaction using account/binding, currency, bundle ID and reference_root; reference_sequence identifies allocations, not new receipts. A bundle paying several profiles produces shared-payer evidence. If any bundle member is inaccessible, inconsistent, unreviewed or outside the selected account scope, hold the entire cluster out and report incomplete coverage; do not expose sibling identities. Collapse duplicate ordinary CRM rows only when exact nonempty reference/account/currency and evidence establish the same cash root; ambiguous roots remain excluded. A current receipt matched to any member excludes that whole cash cluster from prior count. Count one prior cash transaction per cluster per profile, even if multiple allocation rows target that profile. Captured funds are separately labelled observed; they are not statement-verified merely because an SMS exists. The total is the union of eligible CRM payments and valid captured receipts, deduplicated by allocation payment ID or exact account-scoped provider reference/alias. Ambiguous reference clusters are held out and reported, never guessed. Subsidiary free exposure is not a second cash payment. Mixed currencies have separate history groups; no combined monetary total.

Legacy history is computed only when opening the drawer, through a new read-only review-context endpoint. Reuse PhoneNormalizer with the platform prefix, chunk minimal scoped payment columns by ID, normalize every eligible phone rather than substring-match, and cap the scan at 50,000 rows. Return scan completeness, scanned/total rows, as-of timestamp, scope and earliest available dates. Partial results display “At least N”; loading/error/unknown never display zero. Scan newest ID first with a stable upper-ID anchor. A complete result sorts matched transactions by effective paid/provider time and returns its globally latest ten; a partial result labels its rows “matches in scanned records” and never promises globally latest entries. Page through matched rows with an encrypted/signed cursor carrying account, payer fingerprint, current actor scope hash, anchor and next scan ID; reject scope drift. No cache of history, client recommendations or scores in version 1: recompute the current scope, client/link/attribution conflicts and history when opening/refreshing context and before confirmation. React Query may preserve the visible draft while a fresh request runs, but preselection is disabled during stale/loading/failed context. This deliberately trades a bounded detail request for correctness without inventing a source-revision mechanism. Measure the 50,000-row budget before release; lower the scan budget with explicit partial coverage if needed. Queue counts are separately labelled captured receipts, grouped by account/fingerprint, with no legacy scan on polling.

Client confidence and package choice

Keep suggestions separate from CollectionDecisionService::evaluate and all automatic rules. The new service ranks currently permitted, non-archived clients using the table below. Scores are explicit rule points, never a claimed probability or evidence of authorization. Store a rule version in the response. Name similarity and amount alone do not preselect a profile. Collapse multiple evidence sources for the same client; never add points beyond the strongest applicable rule.

Version 1 proposed scoring
EvidenceScorePreselection
Unique current reviewed payer link, with no contradictory identity evidence95 / 100 · HighYes
At least 3 prior successful payments using this number, all linked to one current profile90 / 100 · HighYes, only with complete history
Exact unique current advert-phone match80 / 100 · MediumYes, only with complete conflict checks
One or two prior payments linked to one profile65 / 100 · MediumShow option; staff selects
Name similarity only40 / 100 · LowSearch aid only
Shared phone, disputed attribution, incomplete history or identity conflictsAt most 49 / 100 · Needs choiceNo

Archived/disputed payment_attributions cannot establish a selectable current customer. Revoked/expired payer links cannot support a positive match. Display the competing evidence rather than hiding it. Staff who select a different client see “Selected by you”; the old confidence badge must disappear. Name-only evidence never beats a payer-phone conflict.

Preselect an exact service only when a single current receipt-bound reviewed intent passes existing purchase validation for the selected client, amount and currency. A catalogue price that happens to equal the amount can be highlighted, but must be explicitly selected; equal amounts can buy different durations or negotiated packages. Show current approved quotes and exact catalogue prices in one progressive package area. Existing CollectionPurchaseService validates any submitted selection, including quote approvals and the TZ subsidiary identity requirement. Resolve a unique existing subsidiary link when supported; otherwise retain an explicit chooser, never an invented ID.

Open the purchase choice immediately for receipts requiring review. Payer, client and package appear together; collector reconciliation moves below the review task and remains collapsed. Remember-payer stays unchecked; future standing authority stays a separate manager-only option. Background polling can update evidence but cannot replace staff edits. A newer receipt version shows a refresh/review notice and requires renewed confirmation; preserve inputs through errors. Before POST approval, re-fetch receipt/context, revalidate scope and choice, and pass the current expected_version; the existing backend transaction remains authoritative. Read-only context calls must produce no intents, payer links, payment rows, allocations or audits.

In shadow mode, “Save purchase choice” creates only the explicit receipt-bound reviewed intent via the existing create-intent path and optional explicitly checked payer review. Return and display the saved choice on reopening using its exact account/provider reference and native purchase audit, including an expired-choice state. Payer-link and intent creation must occur in the same account/receipt-locked transaction: after constructing the intent, call CollectionPurchaseService::validate($newIntent, $lockedReceipt, false) before commit, with rollback of intent/link/audit changes on amount, currency, client-state or other validation failure. Use existing unique collection_audit.dedupe_key for the receipt/actor/request key and persist the request payload hash plus saved result; identical retries return the original result, a changed payload with the same key is a 409. Create-intent currently lacks receipt optimistic locking/idempotency: extend this receipt action with expected_version and a staff request key, serialize account/receipt saves, and record/replay the purchase audit result without duplicate authority creation. Require distinct explicit confirmation to replace an existing saved choice, revoke its superseded receipt-bound one-use intent in the same transaction, and reject attempts to replace an allocated purchase through this save path; retain corrections for allocations. Default to reviewed_quote/max_renewals=1 and never create standing authority on shadow save. A retry must return the same saved choice. Changing client/price/quote/subsidiary clears dependent draft fields before save. It leaves decision/activation state unchanged and never invokes /approve. Activation becomes available only after a read-only eligibility preview validates purchase terms through CollectionPurchaseService::validate(..., false), current primary/subsidiary scope and policy, identity/profile holds, existing-payment/fulfillment ownership, and CollectionGate::assertFunds plus assertWrites(..., false) for the exact purchase. Reuse pure validators or extract shared read-only validation from CollectionApprovalService so the preview does not create a reservation or acquire mutation ownership; the reserve transaction still repeats authoritative checks. Return actual blocked reasons; do not use the global capabilities boolean as a receipt-specific authorization. A failed approval never reports success.
