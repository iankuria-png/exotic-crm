## What this is

One HTTPS endpoint at `crm.exotic-online.com/api/mcp` that speaks MCP, and a
Settings workspace that runs it. An AI session registers the endpoint once and
thereafter has a governed view of the CRM: revenue and market analytics, client
lifecycle and retention, ops and error state, and the schema knowledge every
session currently re-learns from `CLAUDE.md`.

Registration is one line per client:

```bash
claude mcp add --transport http exotic https://crm.exotic-online.com/api/mcp --header "Authorization: Bearer $EXOTIC_MCP_TOKEN"
```

```toml
# ~/.codex/config.toml
[mcp_servers.exotic]
url = "https://crm.exotic-online.com/api/mcp"
bearer_token_env_var = "EXOTIC_MCP_TOKEN"
```

Asked "why did new-user revenue fall 3.1% this window?", a session calls
`exotic_revenue_summary`, sees the drop concentrated in two markets, calls
`exotic_market_breakdown` for those, then `exotic_churn_analysis` with
`breakdown=signup_source` — three typed calls, no SQL written, no PII moved. Every
one of those calls appears in the control station within seconds, with its
arguments, row count, payload size and latency.

The station is seven panels inside one Settings tab, following the shape
`AiWorkspacePanel.jsx` already uses — sub-tabs with a live hint on each, so the
nav itself reports state. **Overview** answers is-it-on and is-it-healthy.
**Tokens** issues and revokes credentials. **Tools** is the registry with a
per-tool kill switch. **Data & Privacy** governs what may leave the building.
**Limits** sets the budgets. **Activity** is the searchable audit trail.
**Guide** is the setup and reference documentation, in the product.

Stateless Streamable HTTP — one JSON response per POST, no SSE stream — is what
makes this viable on cPanel. Every request is independent, nothing is long-lived,
and PHP-FPM serves it like any other route.

## Why curated tools rather than schema-plus-SQL

Large surface: many tables, models and migrations. Pointed at raw tables an LLM re-derives
joins, grain and metric definitions on every prompt, so the same question returns
a different number each time and nothing enforces market scope. A named tool with
typed parameters returns the same figure the CEO dashboard returns, because it
calls the same service.

The escape hatch stays, because a fixed tool set cannot anticipate every question.
`exotic_run_reporting_sql` runs model-written SQL through a shared
`App\Services\Ai\SqlSafetyValidator` core — single statement, SELECT only, no
comments, allow-listed `vw_*` views only, forced LIMIT, and an outer projection
that filters `platform_id` server-side so the model cannot widen its own
visibility. The existing validator currently reads `config('ai.reporting_views')`
and `AiInsightsSettingsService` directly, so this work must first split that into
a reusable validation engine plus an explicit `SqlValidationPolicy` value object:
Talk to Your Data passes the AI policy, and MCP passes `mcp_config.sql_hatch`
views/limits/timeouts. This is one shared validator with two policies, not two
validators and not a global config mutation.

The SQL hatch is deliberately stricter than the tool-internal view layer. A view
may contain `client_id` or `deal_id` when it is used only by PHP tools that
pseudonymise before serialisation, but it is not eligible for
`exotic_run_reporting_sql` until a wrapper view removes or replaces those raw
entity IDs. The MCP SQL policy carries a forbidden-output list:
`client_id`, `deal_id`, `payment_id`, `lead_id`, `agent_id`, `user_id`, names,
phones, emails and free-text columns. `platform_id` is the one raw identifier
allowed through, because it is the scope column.

## Identity: handles, not names

Every client, user and lead crosses the boundary as a stable opaque handle. The
model can follow `cli_7f3a9c2e` across a whole session, group it into cohorts and
compare it against others — but the handle carries no name, phone, email, bio or
KYC state, and cannot be reversed outside the CRM.

The same rule applies to SQL results. `platform_id` may cross the boundary raw;
`client_id`, `deal_id`, `lead_id`, `payment_id`, `agent_id` and `user_id` either
leave as handles through curated tools or do not leave at all. A
`ToolResultSanitizer` fails any tool response that still contains raw entity-id
keys or raw-id-bearing URLs, and `SqlValidationPolicy` rejects SQL-hatch views or
projections that return those columns. Its projection check is identifier-aware
(aliases such as `agent_id AS rep` do not bypass it) and runs before the query is
wrapped for market scope.

## Tool catalogue

Namespaced `exotic_*` so the client groups them. `exotic_catalog` is the entry
point: it returns the enabled tool families, the markets this token can see with
their ids and names, the date coverage of the data, and the reporting-view
dictionary — so an agent orients in one call instead of guessing at parameters.

Every tool takes an optional `response_format` of `concise` (default) or
`detailed`, and every list-shaped tool defaults to 50 rows with an explicit
`limit`. Errors are written to steer: an unknown `platform_id` returns the list of
ids this token may use, not a bare 422.

## Observability

same discipline `AiGateway` already applies to `ai_interactions`. Results are
never stored, and arguments are stored only as a redacted shape, so the audit log
cannot itself become a PII store. Refused SQL writes the refusal code, a safe
statement hash and a redacted projection when one can be derived; it does not
persist the raw rejected statement.

## Auth: a token that can only do this

<Callout tone="risk" title="Sanctum abilities are unused in this codebase" body="`tokenCan()` appears nowhere in `app/` or `routes/`, and `config/sanctum.php:57` sets `'expiration' => null`. `createToken(string $name, array $abilities, DateTimeInterface $expiresAt)` — and
`Guard::isValidAccessToken` honours per-token `expires_at` regardless of the null
global. No new token table is required.

## The request-coupling compromise

`CeoDashboardDataService::summary()`, `revenueTrend()`, `marketPie()`,
`agentPerformance()` and `peakHours()` all take an `Illuminate\Http\Request`. That
is how the whole CEO dashboard is built, and rewriting a 1,000-line service to
take parameter arrays would put the dashboard at risk to make an MCP tool tidier.

So the tools do not refactor it. `McpRequestAdapter` builds a synthetic `Request`
from validated MCP arguments and passes it in. This is a deliberate compromise: it
keeps the numbers identical to the dashboard's by construction for admin
org-wide and single-market calls — same code path, same FX handling, same
exclusions — at the cost of an adapter that must know the query-parameter names
each method reads.

Multi-market scoping is owned by `McpDashboardScopeRunner`, not by the adapter.
It resolves the caller's allowed markets, intersects any requested
`platform_ids`, runs the dashboard once for unrestricted admin/org-wide requests,
runs it once for a single market, and fans out across allowed markets for
sub-admin multi-market requests before merging the typed result. Tests pin all
three cases: admin org-wide parity, single-market parity, and sub-admin
multi-market fan-out with no scope widening.

## Steps

Phase 1 is steps 1-3 — the endpoint exists, is safe, and is observable. Phase 2 is
steps 4-7 — the tools that answer real questions. Phase 3 is steps 8-12 — the
remaining domains and the full control station. The implementation order is
strictly sequential from step 1 through step 12, so the grand vision stays visible
while each layer is built on the last. Step 7 is a checkpoint, not a cut line:
transport/auth/audit, revenue and lifecycle tools, Overview, Tokens and Activity
must work before moving on. Then steps 8-12 complete the ops, context, SQL,
privacy, limits and guide surfaces before the MCP station is considered shipped.

## Verification

Beyond `--filter='Mcp'` feature tests:

1. **Real client handshake.** Register the endpoint in both clients against
   staging or local — `claude mcp add --transport http …` then `claude mcp list`,
   and the Codex `config.toml` block. Both must list the enabled tools and the
   three resources from a single `tools/list` / `resources/list`.
2. **Transport compliance.** Feature tests must cover a modern 2026-07-28 POST
   with `MCP-Protocol-Version`, matching `params._meta` protocol version, `Mcp-Method`,
   `Mcp-Name`, deterministic `server/discover`, and successful
   `resultType=complete` on `tools/call`; an older initialize-style client without the protocol
   header; an invalid protocol version; a rejected Origin; and mismatched
   method/name/recognised-param headers returning `HeaderMismatch -32020`. All
   failures return predictable JSON-RPC errors and are logged to `mcp_tool_calls`.
3. **Dashboard parity.** Ask a session for collected revenue over the last 30 days
   across all markets and compare against the CEO dashboard for the same window
   and currency mode. Admin org-wide and single-market calls must match exactly;
   scoped sub-admin multi-market calls must equal the merge of allowed
   single-market dashboard calls and must not include disallowed markets.
4. **Settings actually govern.** With a live session connected, disable
   `exotic_churn_analysis` in the Tools panel; the next `tools/list` in that
   session must omit it. Re-enable and confirm it returns.
5. **PII absence, mechanically.** A feature test calling every tool with
   representative arguments against a seeded database, concatenating all
   responses, asserting the seeded client's name, phone and email appear nowhere.
   A second test reads the SQL text for every MCP allow-listed view and fails if
   it references obvious PII/free-text source columns such as `phone`, `email`,
   `bio`, `notes`, `message`, `body`, `raw_payload`, or `payment_data`. SQL-hatch
   allow-listed views and projections also fail on raw entity IDs other than
   `platform_id`.
6. **Ability isolation.** An `mcp:read` token must 403 against
   `/api/crm/dashboard/ceo/summary`, `/api/crm/setup/run-sync`,
   `POST /api/platforms`, `POST /api/products`, `/api/activate-profile`, and
   `/api/manual-stk-push`; public legacy `GET /api/platforms` and
   `GET /api/products` keep their current unauthenticated responses; a `['*']`
   session token must 401 against `/api/mcp`.
7. **SQL policy separation.** Lower the MCP SQL max row limit and remove one MCP
   reporting view; confirm MCP obeys those changes while Talk to Your Data still
   uses `ai_insights_config` / `config/ai.php` limits and view access.
8. **Refusal path is visible.** `exotic_run_reporting_sql` with
   `SELECT * FROM clients` must be refused, appear in Activity with
   `refusal_reason=sql_validation`, and the error text must name the allow-listed
   views so the agent can retry correctly. The row must contain no raw rejected
   SQL or bearer-looking text.
9. **Legacy payment regression.** Public checkout initiation, callback routes,
   `legacy.payment.callback`, STK auto-activation, `/api/activate-profile`, and
   `/api/manual-stk-push` keep their current successful-path behaviour with a
   normal CRM/session or callback credential; MCP ability isolation must not alter
   the production payment flow.
10. **UI fit.** For each control-station checkpoint, capture desktop and mobile
    Playwright screenshots, assert no horizontal overflow, and verify long labels,
    token names, error reasons and copyable commands do not clip or overlap.
11. **Self-test detects a real break.** Point `DB_RO_*` at a bad host; the self-test
   must fail that one check with a remediation line and leave the others passing.
12. **Rollback drill.** Before production, prove the rollback path locally:
    disable `mcp_config.enabled`, revoke active `mcp:*` tokens, confirm `/api/mcp`
    refuses every call, and document that reporting views stay in place until a
    cleanup migration because dropping views is not needed to stop data egress.
13. **Sequential release path.** Implement and verify steps 1-12 in order. At the
    step 7 checkpoint, run the full backend/client handshake and UI smoke checks
    before starting step 8. At step 12, run `npm run build`, commit `public/build/`,
    push to `origin main`, pull on cPanel, run the MCP migrations, mint a token in
    Settings, then repeat steps 1-12 against production.
