Implementation plan

MCP ingestion point and control station

Expose a governed, pseudonymous, read-only view of the CRM to Codex CLI and Claude Code over one authenticated endpoint, operated entirely from a Settings workspace where every tool, limit, view and token is configurable, every call is observable, and the setup guide lives in the product.

Status audit round 3 — READYOwner Ian KDate 2026-09-10Scope one MCP endpoint on cPanel, 15 curated tools, 3 context resources, 6 new reporting views, scoped tokens, and a seven-panel MCP control station in SettingsNon-goals no write actions of any kind in v1 — no campaign sends, no deal changes, no profile edits; no OAuth authorization server (Codex and Claude Code take a bearer token; the Claude and ChatGPT desktop apps would need OAuth and are deferred); no Laravel 11/12 upgrade; no refactor of CeoDashboardDataService or the other large request-coupled services; no raw table access — the model never sees a base table, only curated tools and vw_* views

What this is

One HTTPS endpoint at crm.exotic-online.com/api/mcp that speaks MCP, and a Settings workspace that runs it. An AI session registers the endpoint once and thereafter has a governed view of the CRM: revenue and market analytics, client lifecycle and retention, ops and error state, and the schema knowledge every session currently re-learns from CLAUDE.md.

Registration is one line per client:

claude mcp add --transport http exotic https://crm.exotic-online.com/api/mcp --header "Authorization: Bearer $EXOTIC_MCP_TOKEN"
# ~/.codex/config.toml
[mcp_servers.exotic]
url = "https://crm.exotic-online.com/api/mcp"
bearer_token_env_var = "EXOTIC_MCP_TOKEN"

Asked "why did new-user revenue fall 3.1% this window?", a session calls exotic_revenue_summary, sees the drop concentrated in two markets, calls exotic_market_breakdown for those, then exotic_churn_analysis with breakdown=signup_source — three typed calls, no SQL written, no PII moved. Every one of those calls appears in the control station within seconds, with its arguments, row count, payload size and latency.

Hand-rolled JSON-RPC, no new dependency

The official laravel/mcp package requires Laravel 11.45+ or 12.41+. This repo is Laravel 10.50.2, so it is unavailable and a framework upgrade is out of scope. MCP over stateless Streamable HTTP is a single POST route handling the core methods this product exposes — server/discover, tools/list, tools/call, resources/list, resources/read — with full control over auth, scoping and audit. initialize is accepted only inside the isolated 2025-era fallback path, never mixed into a modern 2026-07-28 request. It adds zero composer dependencies, which matters because vendor/ is gitignored while composer.lock is tracked: every new package becomes a composer install step in the cPanel deploy. php-mcp/server v3.3 is the fallback if the hand-rolled dispatcher drifts from the spec.

Stateless Streamable HTTP — one JSON response per POST, no SSE stream — is what makes this viable on cPanel. Every request is independent, nothing is long-lived, and PHP-FPM serves it like any other route.

Transport contract to implement, not approximate

Target the current Streamable HTTP shape (MCP-Protocol-Version: 2026-07-28) and accept older clients that omit the header by treating them as 2025-03-26 only after initialize. Every POST must validate Accept: application/json, text/event-stream, Content-Type: application/json, Origin when present, Mcp-Method, Mcp-Name for tools/call and resources/read, params._meta.io.modelcontextprotocol/protocolVersion matching the protocol header, and any recognised Mcp-Param-* against the JSON-RPC body. Successful modern tools/call results include resultType: complete; server/discover, tools/list, resources/list and resources/read keep their own spec-shaped results. Mismatches return a deterministic JSON-RPC error (HeaderMismatch, code -32020). server/discover, tools/list and resources/list must be deterministic and cacheable. Do not mint or require Mcp-Session-Id; protocol-level sessions are gone in the current revision. Add feature tests that send both the modern header set and the older initialize-style client flow used by Claude Code/Codex today.

Why curated tools rather than schema-plus-SQL

Large surface: many tables, models and migrations. Pointed at raw tables an LLM re-derives joins, grain and metric definitions on every prompt, so the same question returns a different number each time and nothing enforces market scope. A named tool with typed parameters returns the same figure the CEO dashboard returns, because it calls the same service.

The escape hatch stays, because a fixed tool set cannot anticipate every question. exotic_run_reporting_sql runs model-written SQL through a shared App\Services\Ai\SqlSafetyValidator core — single statement, SELECT only, no comments, allow-listed vw_* views only, forced LIMIT, and an outer projection that filters platform_id server-side so the model cannot widen its own visibility. The existing validator currently reads config('ai.reporting_views') and AiInsightsSettingsService directly, so this work must first split that into a reusable validation engine plus an explicit SqlValidationPolicy value object: Talk to Your Data passes the AI policy, and MCP passes mcp_config.sql_hatch views/limits/timeouts. This is one shared validator with two policies, not two validators and not a global config mutation.

The SQL hatch is deliberately stricter than the tool-internal view layer. A view may contain client_id or deal_id when it is used only by PHP tools that pseudonymise before serialisation, but it is not eligible for exotic_run_reporting_sql until a wrapper view removes or replaces those raw entity IDs. The MCP SQL policy carries a forbidden-output list: client_id, deal_id, payment_id, lead_id, agent_id, user_id, names, phones, emails and free-text columns. platform_id is the one raw identifier allowed through, because it is the scope column.

Tool output is untrusted input

This is the Supabase/Cursor incident shape: privileged read access, plus attacker-controlled text, plus an outbound channel. This CRM holds attacker-controlled text in client_notes.body, Support Board tickets and WordPress profile bios. No tool returns client- or visitor-authored free text at all. exotic_error_digest returns exception messages, which can embed user input, so they are truncated and stripped of URLs, Authorization: header shapes and bearer/API-key patterns before leaving the server — with those rules shown and adjustable in the Data &amp; Privacy panel.

Identity: handles, not names

Every client, user and lead crosses the boundary as a stable opaque handle. The model can follow cli_7f3a9c2e across a whole session, group it into cohorts and compare it against others — but the handle carries no name, phone, email, bio or KYC state, and cannot be reversed outside the CRM.

The same rule applies to SQL results. platform_id may cross the boundary raw; client_id, deal_id, lead_id, payment_id, agent_id and user_id either leave as handles through curated tools or do not leave at all. A ToolResultSanitizer fails any tool response that still contains raw entity-id keys or raw-id-bearing URLs, and SqlValidationPolicy rejects SQL-hatch views or projections that return those columns. Its projection check is identifier-aware (aliases such as agent_id AS rep do not bypass it) and runs before the query is wrapped for market scope.

Tool catalogue

Namespaced exotic_* so the client groups them. exotic_catalog is the entry point: it returns the enabled tool families, the markets this token can see with their ids and names, the date coverage of the data, and the reporting-view dictionary — so an agent orients in one call instead of guessing at parameters.

Every tool takes an optional response_format of concise (default) or detailed, and every list-shaped tool defaults to 50 rows with an explicit limit. Errors are written to steer: an unknown platform_id returns the list of ids this token may use, not a bare 422.

The registry doubles as the kill switch. Selecting a row opens the inspector: schema, example call, backing service, and the exact views it reads. A disabled tool disappears from tools/list rather than failing at call time, so an agent never plans around a tool it cannot use.

Everything configurable, without a deploy

Configuration follows the pattern AiInsightsSettingsService already establishes: config/mcp.php holds defaults, an IntegrationSetting row keyed mcp_config overrides them, and array_replace_recursive merges the two. Settings wins, so every control in the station is a database write rather than an env change and a redeploy — which matters because cPanel deploys are a manual pull.

Settings overrides config, and a disabled tool is invisible

A tool switched off in the station is filtered out of tools/list entirely rather than left listed and refused on call. An agent that cannot see a tool never plans around it; an agent that sees a tool and gets refused will retry, rephrase and burn calls. The same rule applies to resources and to the SQL escape hatch.

Observability

Every call writes one row, whether it succeeds, is refused or is throttled — the same discipline AiGateway already applies to ai_interactions. Results are never stored, and arguments are stored only as a redacted shape, so the audit log cannot itself become a PII store. Refused SQL writes the refusal code, a safe statement hash and a redacted projection when one can be derived; it does not persist the raw rejected statement.

Auth: a token that can only do this

Sanctum abilities are unused in this codebase

tokenCan() appears nowhere in app/ or routes/, and config/sanctum.php:57 sets 'expiration' => null. So today createToken('crm-session') in AuthController mints a non-expiring token with ['*'] abilities. Minted the same way, an MCP token would be a permanent full-power CRM credential in a config file on a laptop — and because no CRM route checks abilities, a mcp:read token would authenticate against every /api/crm/* route including admin-only ones. Both halves need fixing: the MCP endpoint must require the ability, and the CRM routes must reject tokens that carry it.

Sanctum 3.3.3 already supports what is needed — createToken(string $name, array $abilities, DateTimeInterface $expiresAt) — and Guard::isValidAccessToken honours per-token expires_at regardless of the null global. No new token table is required.

The request-coupling compromise

CeoDashboardDataService::summary(), revenueTrend(), marketPie(), agentPerformance() and peakHours() all take an Illuminate\Http\Request. That is how the whole CEO dashboard is built, and rewriting a 1,000-line service to take parameter arrays would put the dashboard at risk to make an MCP tool tidier.

So the tools do not refactor it. McpRequestAdapter builds a synthetic Request from validated MCP arguments and passes it in. This is a deliberate compromise: it keeps the numbers identical to the dashboard's by construction for admin org-wide and single-market calls — same code path, same FX handling, same exclusions — at the cost of an adapter that must know the query-parameter names each method reads.

Multi-market scoping is owned by McpDashboardScopeRunner, not by the adapter. It resolves the caller's allowed markets, intersects any requested platform_ids, runs the dashboard once for unrestricted admin/org-wide requests, runs it once for a single market, and fans out across allowed markets for sub-admin multi-market requests before merging the typed result. Tests pin all three cases: admin org-wide parity, single-market parity, and sub-admin multi-market fan-out with no scope widening.

Ops data stays out of the SQL escape hatch

SqlSafetyValidator::wrapWithScope filters on platform_id, so every allow-listed SQL-hatch view must expose one and must be aggregate/id-safe. Tool-internal views containing client_id or deal_id are not automatically SQL-hatch views; the SQL allow-list stays purely business data.

Steps

Phase 1 is steps 1-3 — the endpoint exists, is safe, and is observable. Phase 2 is steps 4-7 — the tools that answer real questions. Phase 3 is steps 8-12 — the remaining domains and the full control station. The implementation order is strictly sequential from step 1 through step 12, so the grand vision stays visible while each layer is built on the last. Step 7 is a checkpoint, not a cut line: transport/auth/audit, revenue and lifecycle tools, Overview, Tokens and Activity must work before moving on. Then steps 8-12 complete the ops, context, SQL, privacy, limits and guide surfaces before the MCP station is considered shipped.

  3. Q3Should a sub-admin's token see org-wide aggregates?single

    Scope resolves from the owning user, so a sub_admin token is narrowed to their markets. Correct for row-level data, but it means they cannot see the company total even as a single number.

    • Yes — org-wide totals, market-scoped rowsMore useful for a market lead, but introduces a second scoping rule every tool must implement correctly.
